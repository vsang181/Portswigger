# Injecting OS commands

Consider a shopping application that allows users to check whether an item is in stock at a specific store by requesting a URL with query parameters:

```
https://insecure-website.com/stockStatus?productID=381&storeID=29
```

To retrieve the stock information, the application queries legacy back-end systems. For historical reasons, the server implements this functionality by passing the user-supplied `productID` and `storeID` values directly as arguments into a system shell command:

```
stockreport.pl 381 29
```

The script executes on the server, outputs the stock status for the requested item, and the web application returns that output directly in the HTTP response to the user.

## Why This Implementation Is Vulnerable

- **Direct Shell Execution**: Instead of using safe, parameterized APIs or native language functions, the application concatenates raw HTTP query parameters (`381` and `29`) straight into an operating system command string.

- **No Input Sanitization**: Because the server fails to validate that `productID` and `storeID` contain only numbers and does not strip or escape shell metacharacters an attacker can break out of the intended arguments and append arbitrary OS commands.

- **In-Band Output (Direct Feedback)**: Since the application reflects the output of the `stockreport.pl` command directly back to the user in the HTTP response, any output generated by an injected command (such as `whoami`) will also appear directly in the response.
